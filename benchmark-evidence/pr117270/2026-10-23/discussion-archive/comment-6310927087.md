## Local benchmark for PR #117270

Measured complete local `GRANT` and `REVOKE` operations using a synthetic ACL matching the aggregate size recorded in a production snapshot on 2026-09-18. This is local Linux ARM64/Docker evidence, not a production or performance-CI result.

### Setup

- A: official ARM Release CI artifact for the exact parent, `dd7889a115c63e16f3bcbc9f843e4633fb2fe1e0`.
- B: locally built PR head, `de8c62d3fe99ad722f89346ef6a9e5cb77531278`. The source difference consists only of this PR.
- Source identity is checked against `system.build_options.GIT_HASH`, which CMake reads from the checkout. The local B build retains the committed release marker in `VERSION_GITHASH`; both fields and version strings are retained in the raw results.
- Matched Clang/Clang++ and LLD 22.1.8, CMake 4.4.2, `RelWithDebInfo`, `-O3`, ThinLTO, ARM target flags, XRay and reported feature flags. B limits linker worker concurrency to fit the local build environment; optimization remains enabled. B was built locally using the same CI-derived builder image, rather than being an official CI binary.
- Build-flag comparison normalizes linker worker counts, the local ThinLTO backend-cache directory and the output-directory prefixes of the two compiler-rt archives; raw `system.build_options` values are retained.
- Apple M5 Max, 18 CPU cores, 128 GiB host RAM, AC power; macOS 27.0.1 and Docker Desktop 4.96.0, configured with 90 GiB VM memory. Each benchmark container uses the same 4 vCPUs and 6 GiB limit. Other existing Docker services were paused (11) or stopped (2) before the accepted matrix, with periodic state checks rejecting unpaused unrelated containers; the macOS host is not claimed to be exclusive.
- One user: 75,123 explicit privilege rows across 15,580 table paths; one enabled/default role: 471 rows across 465 table paths. No column grants or partial revokes. Counts are checked through `system.grants` for every run.
- The fixture is synthetic, not an exact production ACL dump: owner/read-only grants share one database, with role paths spread over direct-grant paths. The same fixture hash is verified on A and B.
- The fixture does not seed `WITH GRANT OPTION`; the production grant-option distribution and exact database/table-name topology were not captured in the historical aggregate measurements.
- Persistent HTTP named sessions remain alive throughout each run. Every session uses the same role. Session existence is checked with `session_check=1`.
- `shared` keeps the same context parameters across sessions. `distinct` assigns a different default database to each session to create distinct `ContextAccess` instances without changing effective privileges. Connection count alone must not be interpreted as the number of distinct access contexts.
- The session count is the number of persistent named sessions, not an exact count of all retained access contexts. In this harness, B records one calculation plus N cache hits for N distinct named sessions (including N=1); shared sessions record one calculation and zero hits.
- The HTTP named session retains its default-database context; requests use copied query contexts with the requested database. The existing access-context cache can retain those database-specific contexts. This explains N+1 calculation-path calls in the distinct case, including two calls for one named session; it is not a single-access-context speedup.
- Each case runs in fresh sequential A/B/B/A containers. Each block has two warm-up grant/revoke pairs and ten measured pairs: 20 measured grants and 20 measured revokes per variant and case. P95 uses the nearest-rank definition.
- The permission being changed genuinely alternates between absent and present. All existing sessions check the resulting permission after every operation, and unrelated write access remains denied. Validation, fixture setup and server startup are outside timed sections.
- Timings use a client inside the isolated container over loopback. There is no `ON CLUSTER`, Keeper or distributed DDL queue in this measurement. No compilation runs concurrently with the measured matrix.

### Interpretation and repeatability

Verdict: local-only evidence. The distinct-context cases measure the intended reuse across access contexts; the shared-context cases control for reuse already provided by the existing context cache. Small differences in those controls should be read alongside the block variation, not presented as a general grant-speed improvement.

For distinct context parameters, median `GRANT` speedups are 2.10×, 15.55× and 65.14× at 1, 10 and 50 named sessions. Query CPU time falls in the same direction, and the improvement is present in both blocks. The shared-parameter controls show no consistent improvement beyond their observed block variation.

### Scope and reproducibility

The shared-parameter case controls for the existing `ContextAccess` cache. The distinct-parameter case exercises reuse across different contexts with the same effective rights; it is not a claim that every production connection creates a unique context. This first matrix covers direct user privilege changes, not role changes or concurrent access-entity writers.

The results do not predict the original production `GRANT ON CLUSTER` latency: hardware, ACL shape, live context count, contention and DDL queueing differ. Query-attributed memory is available in the raw summary, but is not reported as process peak RSS. Linux delay accounting is unavailable in this environment, so CPU-wait counters are not used as evidence.

Artifacts: `run_case.py`, `run_matrix.py`, `build_B.sh`, `binary_manifest.json`, `host.json`, per-run `fixture.sql` / `dataset.json` / `samples.jsonl` / `result.json`, and the complete matrix manifest and summary. Pilot results and an earlier full matrix affected by automatic startup of unrelated containers were excluded. Per-block medians are retained in `summary.csv` to inspect run-to-run variation.
